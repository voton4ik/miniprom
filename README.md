# miniprom

![CI](https://github.com/voton4ik/miniprom/actions/workflows/ci.yml/badge.svg)
![Go](https://img.shields.io/badge/Go-1.26-00ADD8?logo=go&logoColor=white)

Маленький сборщик метрик в духе Prometheus. Ходит по вашим сервисам, забирает
метрики в текстовом формате Prometheus, складывает их в память как временные ряды
и отдаёт наружу через HTTP API и простенькую веб-страницу.

Написан на чистом Go, без единой сторонней зависимости — только стандартная
библиотека. Это не замена настоящему Prometheus, а компактная и понятная его
версия: удобно, когда хочется быстро посмотреть, что там с метриками, или
разобраться, как подобные штуки устроены внутри.

## Возможности

- Опрашивает несколько целей одновременно, каждую в своей горутине.
- Разбирает стандартный текстовый формат экспозиции Prometheus (`# HELP`, `# TYPE`,
  метки, `+Inf`/`NaN` и экранирование в значениях меток).
- Хранит историю значений в памяти и сам чистит старые данные по сроку хранения.
- Для каждой цели добавляет служебные метрики `up` и `scrape_duration_seconds` —
  так же, как настоящий Prometheus.
- Отдаёт мгновенные значения и диапазоны через JSON API.
- Показывает состояние целей и метрики на веб-странице с автообновлением.
- Мониторит сам себя: на `/metrics` лежат его собственные показатели.
- Structured-логи через `log/slog`, health-проверки `/healthz` и `/readyz`,
  корректное завершение по сигналу.

## Архитектура

```
   цель /metrics ┐
   цель /metrics ┼─▶ scraper (горутины) ─▶ storage (TSDB в памяти) ─▶ api ─▶ браузер / curl
   цель /metrics ┘
```

- `internal/parser` — разбирает текстовый формат Prometheus в набор метрик.
- `internal/scraper` — по таймеру опрашивает цели, каждую в отдельной горутине,
  и складывает результат в хранилище.
- `internal/storage` — потокобезопасное хранилище временных рядов с удалением
  устаревших точек.
- `internal/api` — HTTP-обработчики и веб-страница.
- `internal/config` — чтение и проверка конфигурации.
- `cmd/miniprom` — точка входа, связывает всё вместе.
- `examples/exporter` — демонстрационный сервис с метриками для тестов.

## Быстрый старт

### Docker

Самый простой способ — поднять всё разом: сам miniprom и демо-сервис с метриками.

```bash
git clone https://github.com/voton4ik/miniprom.git
cd miniprom
docker compose up --build
```

Дальше открывайте http://localhost:9099 — там уже видны обе цели и их метрики.

### Локально

Нужен Go 1.26 или новее.

В одном терминале запустите демо-экспортёр — сервис, который отдаёт несколько
меняющихся во времени метрик:

```bash
go run ./examples/exporter
```

А в другом — сам miniprom:

```bash
go run ./cmd/miniprom -config config.json
```

И снова открывайте http://localhost:9099.

Если удобнее через `make`:

```bash
make exporter   # демо-сервис
make run        # miniprom
```

## Веб-интерфейс

На главной странице две части: список целей с индикатором доступности (сколько
метрик собрано, за сколько миллисекунд, когда последний раз) и просмотр метрик —
выбираете имя, при желании фильтруете по меткам и смотрите последние значения.
Состояние целей обновляется само раз в несколько секунд.

## HTTP API

Всё, что показывает веб-страница, доступно и напрямую.

**Список имён метрик**

```bash
curl localhost:9099/api/metrics
```

**Последние значения метрики** (можно отфильтровать по меткам):

```bash
curl "localhost:9099/api/query?metric=http_requests_total"
curl "localhost:9099/api/query?metric=up&labels=job=demo"
```

**История за окно времени**

```bash
curl "localhost:9099/api/range?metric=room_temperature_celsius&range=5m"
```

**Состояние целей**

```bash
curl localhost:9099/api/targets
```

**Собственные метрики miniprom** (в формате Prometheus):

```bash
curl localhost:9099/metrics
```

**Проверки здоровья**

```bash
curl localhost:9099/healthz   # жив ли процесс:     {"status":"ok"}
curl localhost:9099/readyz    # готов ли к работе:  {"status":"ready"}
```

`/readyz` отвечает `503`, пока не прошёл первый цикл сбора — удобно для
readiness-проб в Kubernetes.

## Конфигурация

Основной конфиг — обычный JSON. Пример лежит в [config.json](config.json):

```json
{
  "listen_addr": ":9099",
  "scrape_interval": "5s",
  "retention": "1h",
  "timeout": "3s",
  "targets": [
    { "job": "demo", "url": "http://localhost:9100/metrics" },
    { "job": "miniprom", "url": "http://localhost:9099/metrics" }
  ]
}
```

| Поле | Смысл |
|------|-------|
| `listen_addr` | адрес, на котором miniprom поднимает HTTP-сервер |
| `scrape_interval` | как часто опрашивать цели |
| `retention` | сколько хранить данные, потом они удаляются |
| `timeout` | таймаут на один запрос к цели (должен быть меньше интервала) |
| `targets` | список целей: `job` — имя, `url` — откуда забирать метрики |

Длительности пишутся строкой в формате Go: `5s`, `500ms`, `2m`, `1h`.

Уровень логирования задаётся переменной окружения `MINIPROM_LOG_LEVEL`
(`debug`, `info`, `warn`, `error`; по умолчанию `info`):

```bash
MINIPROM_LOG_LEVEL=debug go run ./cmd/miniprom -config config.json
```

Для запуска в Docker используется [config.docker.json](config.docker.json) —
он отличается только адресами целей (внутри сети compose сервисы видны по именам,
а не по `localhost`).

## Остановка

miniprom завершается аккуратно и не бросает работу на полуслове:

```
SIGINT / SIGTERM
      │
      ├─▶ отмена общего context
      │
      ├─▶ HTTP-сервер перестаёт принимать новые запросы и до 5 секунд
      │   доводит до конца текущие
      │
      ├─▶ горутины скрейпера видят отменённый context и выходят
      │
      └─▶ WaitGroup дожидается их всех  →  процесс завершён
```

Все фоновые горутины получают один и тот же `context.Context`, поэтому утечек не
остаётся: по сигналу они гарантированно останавливаются, а `WaitGroup` не даёт
процессу выйти раньше времени.

## Тесты

```bash
go test ./...          # или make test — с флагом -race
make cover             # тесты + отчёт о покрытии
```

Покрыты критичные части: парсер (валидные и битые метрики, метки, `+Inf`/`NaN`,
пустой ответ), хранилище (включая конкурентный доступ под `-race`), скрейпер
(успех, таймаут, ответ `500`) и HTTP API (`200`/`400`/`404`, health-проверки).

## Структура проекта

```
cmd/miniprom        точка входа
internal/parser     парсер формата Prometheus
internal/storage    хранилище временных рядов
internal/scraper    конкурентный сбор метрик
internal/api        HTTP API + веб-интерфейс
internal/config     конфигурация
examples/exporter   демонстрационный сервис
```

## Технические решения

**Почему хранилище в памяти, а не полноценная TSDB?**
Цель проекта — показать сбор, парсинг и отдачу метрик, а не написать ещё одну
базу. In-memory-хранилище с ретеншеном закрывает эту задачу и не тащит за собой
работу с диском и форматами хранения.

**Почему `sync.RWMutex`?**
К хранилищу одновременно пишут горутины скрейпера и читают HTTP-обработчики.
Чтений заметно больше, чем записей, поэтому `RWMutex` (много читателей
параллельно, писатель эксклюзивно) здесь уместнее обычного мьютекса.

**Почему JSON, а не флаги окружения для целей?**
Список целей — это массив с полями, его неудобно и некрасиво держать в
переменных окружения. Файл конфигурации ближе к тому, как это сделано в самом
Prometheus, а через окружение настраивается только уровень логов.

**Почему без зависимостей?**
Стандартной библиотеки Go хватает на всё: HTTP-сервер и клиент, парсинг,
логирование (`log/slog`), конкурентность. Меньше зависимостей — меньше рисков и
проще собирать.

## Ограничения

- Данные живут только в памяти: после перезапуска история теряется.
- Нет своего языка запросов вроде PromQL — только выборка по имени и меткам.
- Нет алертинга и агрегаций (rate, sum и т.п.).
- Формат экспозиции поддержан в разумном объёме, но не на 100% спецификации
  (например, метки-timestamp у сэмплов игнорируются).

## Планы на будущее

- Персистентность на диск, чтобы история переживала перезапуск.
- Простые агрегатные функции поверх диапазонов.
- Графики прямо в веб-интерфейсе.
- Экспорт собранных метрик обратно в формате Prometheus для федерации.
